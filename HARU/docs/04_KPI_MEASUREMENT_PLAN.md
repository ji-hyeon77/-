# HARU KPI 정의와 평가표

핵심 제품 질문은 사용자가 필요한 항목을 기록하고 진료 요약에서 다시 정확히 찾을 수 있는가다. **실제 사용자 KPI는 모두 미측정**이다. 아래 기능 점검 수치는 가상 데이터와 단일 QA 환경에서 얻었으며 사용자 성과와 별도다.

## 핵심 지표

| 지표 | 정의와 분모 | 목표 가설 | 실제 사용자 결과 | 이번 기능 QA 관찰 |
|---|---|---|---|---|

기록 완료율의 유효 최초 시도는 제공된 정상 가상값을 이용하는 한 과업의 첫 시도다. 유효 과업 도중 발생한 입력 오류와 포기는 실패로 포함하고 제외하지 않는다. 처음부터 오류 차단을 시험하도록 지정한 부정 과업과 중복 재시도는 별도 층으로 보고한다. UI-07의 증상 미선택 저장은 오류 차단 과업으로 분리했으며 이후 명시적 증상 없음 저장은 정상 기능 확인이다. 위 6회는 사용성 프로토콜로 모집한 최초 시도 결과가 아니므로 사용자 KPI 계산에 넣지 않는다.

데이터 보존율은 값 하나만 같아도 성공으로 보지 않는다. ID 날짜 값 측정 시점 시간이 모두 같아야 한다. 의도한 편집 삭제와 실제 손실을 구분하고 예상했던 복원 추가값도 별도로 센다. 정상 복원 5/5로 비정상 입력 거부나 모든 데이터 안전성을 입증하지 않는다. A31~33은 오히려 비정상 자료 수용 실패를 보여준다.

## 수동 수집 양식

`participant_code scenario_id attempt_index started_at ended_at completed_without_help help_count error_category value_found_correctly notes`

사용자 KPI는 최초 시도 기준으로 참여자 수 분자 분모를 함께 보고한다. 재시도와 도움을 받은 완료는 따로 표시한다. 소요시간은 성공 과업 중앙값과 함께 실패 중단 건수를 보고해 빠른 성공 사례만 남는 편향을 드러낸다. 날짜와 시간은 평가 환경 시간대를 기록한다.

## 후속 계측 설계

`record_start` `record_save_success` `record_validation_error` `summary_open` `summary_value_found`를 평가용 가상 task_id와 오류 유형으로 연결하는 방식을 제안한다. 마지막 정보 확인 여부는 단순 화면 열기 이벤트로 대체하지 않는다. 현재 앱에는 이 자동 계측을 추가하지 않았다. 건강수치 질문 원문 이름 병원명은 외부 분석으로 전송하지 않는다.

## 결과에 따른 제품 판단

기록 실패는 입력 단계와 저장 피드백을 먼저 개선한다. 요약 찾기 실패는 홈 진입과 기간 선택을 먼저 검토한다. 데이터 불일치와 응급 오해는 후속 배포 전에 수정하고 회귀 시험한다. 전후 체중의 의미를 혼동하면 라벨과 시점을 다시 설계한다. AI는 기본 기록 흐름과 안전 경계의 확인 후 별도 타당성을 검토한다.

실사용 유지율 기록 부담 감소와 임상 효과는 현재 결과로 주장하지 않는다. 이전 47개 시험 기록과 이번 35개 코드 시험 어느 쪽도 사용자 KPI 달성 근거가 아니다.
